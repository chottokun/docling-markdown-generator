# RAG最適化に向けたMarkdown/YAML形式の改良提案 (RAG Optimization Proposal)

RAG (Retrieval-Augmented Generation) における検索精度と回答品質を向上させるため、現状のDocling出力形式をさらにLLMフレンドリーかつ構造的に拡張するための改良案を以下に提案します。

## 1. メタデータ (YAML Frontmatter) の拡充

現状は `title` のみが付与されていますが、検索時のフィルタリングや、LLMがコンテキストをより深く理解するために以下のフィールドを追加することを提案します。

### 改良案
```yaml
---
title: ドキュメントの正式名称
document_type: 契約書 / 技術論文 / 報告書 (自動分類)
creation_date: 2024-05-20
author: 執筆者名
summary: ドキュメント全体の3行要約 (LLMによる生成を想定)
keywords: [RAG, Markdown, Docling]
page_count: 12
language: ja
---
```
- **メリット**: ベクトル検索だけでなく、メタデータフィルタリング（ハイブリッド検索）の精度が向上します。

## 2. Markdown KV (Key-Value) 形式の導入

非構造化テキストの中から、特定の重要な情報を「属性: 値」の形式で明示的に抽出します。特に、請求書やフォーム形式のドキュメントにおいて有効です。

### 改良案
ドキュメントの冒頭、または各セクションの直後に以下のようなブロックを挿入します。

```markdown
## Key Information
- **Document ID**: REF-99021
- **Total Amount**: ¥55,000
- **Due Date**: 2024-06-30
- **Status**: Pending
```

- **メリット**: LLMが特定の値を参照する際の「ハルシネーション（幻覚）」を抑制し、正確なデータ抽出を容易にします。

## 3. ページ境界マーカーと座標情報の付与 (Chunking Optimization)

RAGにおいて、ドキュメントを分割（チャンキング）する際、ページ境界を跨ぐと文脈が途切れることがあります。また、回答の根拠として「何ページのどのあたり」という情報が求められるケースが増えています。

### 改良案
```markdown
<!-- PAGE_START 1 -->
# 第1章 序論
...
<!-- PAGE_END 1 -->

<!-- PAGE_START 2 -->
## 1.1 背景
...
```

- **メリット**:
  - ページ単位のチャンキングが可能になる。
  - 回答に「(p.1参照)」といった正確な引用元を付加できる。

## 4. VLMによる画像・図表のセマンティック記述

現在は `![キャプション](path)` のみですが、画像内のテキストや図の意味をLLMが理解できる形で記述します。

### 改良案
```markdown
![図1: システム構成図](images/fig1.png)
> **Image Analysis**: この図は、ロードバランサー、3つのWebサーバー、および冗長化されたデータベース構成を示すシステムアーキテクチャ図です。各コンポーネントはHTTPSで通信しています。
```

- **メリット**: 画像情報が検索対象に含まれるようになり、図表に関する質問への回答精度が劇的に向上します。

## 5. テーブル表現のさらなる最適化

現在はHTML形式を推奨していますが、非常に巨大なテーブルの場合、トークン消費が激しくなります。

### 改良案
- **Table Summary**: テーブルの直前に内容の要約（例：「2023年度の地域別売上推移を示す表。関東圏が前年比120%で最大」）を挿入。
- **Selective Formats**: 構造が単純な場合はMarkdown形式、複雑な結合がある場合のみHTML形式を選択的に使用。

## 改良のロードマップ案

1.  **Phase 1 (短期)**: YAML Frontmatterの拡張（page_count, language等）とページ境界マーカーの導入。
2.  **Phase 2 (中期)**: 主要な属性の自動抽出による「Key Information」セクションの追加。
3.  **Phase 3 (長期)**: VLM（Vision Language Model）連携による画像のテキスト記述の統合。
